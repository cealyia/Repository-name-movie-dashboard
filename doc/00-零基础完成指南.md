## 3. 第二天：搞懂数据（这是答辩最容易被问的）

### 3.1 自己查一遍

打开 MySQL 命令行（或 VS Code 的 MySQL 插件）：

```sql
USE movie_dashboard;

-- 1. 总共有多少行？老师一定会问
SELECT COUNT(*) FROM fact_rating;            -- 100836

-- 2. 数据跨了多少年？
SELECT MIN(rated_date), MAX(rated_date) FROM fact_rating;   -- 1996-03-30, 2018-09-24

-- 3. 每个类型有多少部影片？
SELECT g.genre_name, COUNT(*) c
FROM rel_movie_genre rg JOIN dim_genre g ON g.genre_id = rg.genre_id
GROUP BY g.genre_name ORDER BY c DESC;

-- 4. 评分最高的 5 部（至少 50 条评分）
SELECT m.title, ROUND(AVG(r.score),2) avg_score, COUNT(*) c
FROM fact_rating r JOIN dim_movie m ON m.movie_id = r.movie_id
GROUP BY m.movie_id, m.title
HAVING c >= 50
ORDER BY avg_score DESC LIMIT 5;
```

### 3.2 三个必须能讲清的问题

**Q：为什么是 5 张表，不是 1 张？**
> 因为评分数据里有大量重复信息（片名、类型）。如果全塞一张表，一部影片的片名要重复几百次，
> 改一个片名要改几百行。拆成「维度表存描述信息 + 事实表存行为记录」，
> 就是数据仓库里最常用的星型模型，查询时用 `JOIN` 拼回来。

**Q：10 万行查询会不会很慢？**
> 不会。第一，聚合在 SQL 里做，Java 只接收几十行结果；
> 第二，`fact_rating` 上建了 `(movie_id, rated_date)`、`rated_date`、`rated_month` 索引；
> 第三，分页用 `LIMIT/OFFSET`，不会一次查全部。
> 实测每个接口 50–200 ms。

**Q：`rated_date`、`rated_month` 不是重复存了吗？**
> 是冗余，故意的。`rated_at` 是 DATETIME，按月分组要 `DATE_FORMAT(rated_at,'%Y-%m')`，
> 10 万行每行算一次函数用不上索引。导入时直接把月份算好存成 `CHAR(7)`，
> 查询就变成 `GROUP BY rated_month`，能走索引。这叫"空间换时间"。

## 4. 第三天：看懂后端（阅读顺序很重要）

### 4.1 一条请求是怎么走的

以「评分趋势」为例，跟着这条线看一遍，后端就通了：

```
浏览器 fetch('/api/stats/trend?...')
   ↓
StatsController.trend()          controller/StatsController.java:60  ← 只做参数接收和返回
   ↓
StatsService.trend()             service/StatsService.java:105       ← 校验参数、补默认值
   ↓
StatsMapper.selectTrend()        mapper/StatsMapper.java:57          ← 接口，没有实现
   ↓
StatsMapper.xml <select id="selectTrend">                            ← 真正的 SQL
   ↓
MySQL → List<TrendPointVO> → Result.ok() → JSON
```

**关键点：Controller 里不写业务逻辑，Service 里不写 SQL，SQL 只在 XML 里。**
这就是任务书要求的"分层清晰"。

### 4.2 五个必须看懂的地方

| # | 位置 | 看什么 | 为什么重要 |
| --- | --- | --- | --- |
| 1 | `common/Result.java` | `code/message/data/timestamp` | 所有接口统一返回，前端只判断 `code===200` |
| 2 | `common/GlobalExceptionHandler.java` | 400/404/500 怎么来的 | 答辩会问"参数错了返回什么" |
| 3 | `mapper/StatsMapper.xml` 的 `<sql id="movieAgg">` | 公共 CTE 片段 | 所有图表口径一致的秘密 |
| 4 | `common/SortWhitelist.java` | 为什么不能直接拼前端传的列名 | SQL 注入 |
| 5 | `config/WebConfig.java` | CORS + 静态资源映射 | 跨域问题怎么解决的 |

### 4.3 核心 SQL 讲解（背下来一段就够）

`StatsMapper.xml` 里这段是整套看板的地基：

```sql
WITH movie_agg AS (
    SELECT m.movie_id, m.title, m.release_year,
           COUNT(r.rating_id) AS rating_count,
           AVG(r.score)       AS avg_score
    FROM dim_movie m
    LEFT JOIN fact_rating r
           ON r.movie_id = m.movie_id
          AND r.rated_date >= #{from} AND r.rated_date <= #{to}
    WHERE 1 = 1
      -- 类型、年份、关键字等动态条件
    GROUP BY m.movie_id, m.title, m.release_year
    HAVING 1 = 1
      -- 评分区间条件
)
```

讲法：
> 先用 CTE 把"符合筛选条件的影片 + 它们在所选时间段内的评分数和平均分"算成一张临时表，
> 后面的 KPI、趋势、类型对比、TOP10 全都从这张表出发。
> 这样不管用户怎么筛，所有图表的统计口径都是同一套，不会出现"KPI 说 100 部、图表说 98 部"。

## 5. 第四天：看懂前端

### 5.1 三个文件的分工

| 文件 | 职责 | 类比 |
| --- | --- | --- |
| `js/api.js` | 拼参数、发请求、拆 Result、抛错误 | 后勤 |
| `js/charts.js` | 把数据变成 ECharts 的 option | 美工 |
| `js/app.js` | 保存筛选状态、绑定事件、调度上面两个 | 指挥 |

### 5.2 数据流

```
用户点"科幻" chip
   ↓
app.js  toggleGenre()   → state.filters.genres = ['科幻']
   ↓
buildQuery()            → { genres:['科幻'], dateFrom:'2015-01-01', ... }
   ↓
Promise.all([ overview, trend, genres, ratingDistribution, top, tags, heatmap, movies ])
   ↓
charts.js renderXxx()   → chart.setOption(...)
```

**为什么一次发 8 个请求？** 因为每个图表的数据维度不同，后端拆成独立接口更清晰；
浏览器并发 8 个请求、每个 100 ms，用户感知不到。

### 5.3 图表联动怎么做的

```js
charts.genre.on('click', function (params) {
    toggleGenre(params.name);   // 点柱子 = 点筛选器，走同一条刷新逻辑
});
```

讲法：
> 图表点击不是"前端过滤数据"，而是把点击的维度写回筛选状态，再重新请求后端。
> 这样点柱子和点左侧筛选器的结果完全一致，也不会出现"前端过滤后 KPI 没变"的 bug。

| 下载依赖卡住 | 网络问题 | 换手机热点；或在 `settings.xml` 配阿里云镜像 |
| 页面 404 | `web/` 目录不在启动目录下 | 必须在项目根目录启动 |
| 中文变成 `???` | 数据库字符集 | 建库时已指定 utf8mb4，导入用 `--default-character-set=utf8mb4` |
| 筛选后图表不动 | 浏览器缓存了旧 JS | `Ctrl + F5` |
| `Swagger` 打不开 | 路径写错 | 是 `/swagger-ui.html`，不是 `/swagger-ui/` |

## 10. 时间不够时的保底方案

如果只剩 3 天，按这个顺序砍：

1. **保命**：工程能启动 + 5 个接口 + 5 类图表 + 筛选联动 + 10 万行数据（这些是及格线）。
2. **保分**：文档五部分齐全 + AI 记录 10 条以上 + Git 提交 10 次以上。
3. **可砍**：词云（换成柱状）、雷达图、热力图、移动端适配。

但**不要砍**：`SELECT COUNT(*)` 的 10 万行、统一 Result、README 启动步骤 —— 这三项是硬性检查点。
